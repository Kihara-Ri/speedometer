# 轨道交通到站推测与反馈

更新：2026-10-22（`rail-stop-v2`）。实现：[RailArrivalRecognizer.swift](../Sources/SpeedCore/RailArrivalRecognizer.swift)。

## 行为

测速并记录期间自动观察，完整运行周期重复两次后建立“疑似轨道交通”上下文。在满足持续制动与停稳证据后，顶部出现“可能到站了？”，提供“是，到站了”和“不是”。同一次停车只询问一次，最多显示 30 秒；恢复行驶、超过 3 秒的数据中断、停止记录也会收起；单个异常定位点不会收起。

确认后自动添加“确认到站”标记，标记时间取开始持续低速的时刻，点击时间另存。否认保留为负样本；超时或未操作保留为未确认。历史行程的“到站推测与反馈”可查看回答。当前主页面没有手动标记入口；漏检需要结合独立的现场时刻记录分析。

## 初始实验参数

以下是保守启发式参数，尚未使用真实列车行程标定，不是识别准确率或概率。

| 条件 | 当前值 |
|---|---|
| 速度输入 | 测速滤波器接受的定位速度；不使用预测速度 |
| 速度/水平精度 | ≤1 m/s、≤35 m |
| 观测年龄 | ≤1.5 秒 |
| 连续观测最大间隔 | 3 秒（容许 1 Hz 定位缺一帧及送达延迟）；超出只中断当前单段运行 |
| 跨站上下文最大断档 | 10 秒无有效速度即清空已完成运行计数 |
| 巡航 | `speed - speedAccuracy ≥ 8 m/s` 连续 15 秒 |
| 单段运行 | 至少 25 秒，峰值至少 10 m/s |
| 制动 | 至少 6 秒，速度下降至少 7 m/s；明显再次加速或非停稳状态匀速超过 2 秒中断制动 |
| 异常速度变化 | 相对上一可信观测小于 −2.5 或大于 3 m/s² 时丢弃该点 |
| 停稳证据 | `speed + speedAccuracy ≤ 0.8 m/s` 连续至少 4 秒 |
| 手机运动 | 最近 1 秒有有效去重力加速度和角速度；安静持续至少 3 秒 |
| 安静门限 | 加速度模长 ≤0.06 g，角速度模长 ≤0.2 rad/s |
| 明显手机转动 | >0.6 rad/s，废弃当前制动与巡航确认 |
| 重复周期 | 连续两个完整周期，停车时刻间隔 40…600 秒 |

步行、跑步和骑行活动证据与时钟重置会清空全部运行上下文；原地静止不能单独确定到站。

单个异常观测按三级处理（v2）：

1. 滤波器拒绝、精度超限或速度跳变的孤立定位点只被跳过，不中断当前运行，也不收起已显示的提示。
2. 连续坏点或无定位超过 3 秒，中断当前单段运行并收起提示，但保留已完成运行计数与上次停车时刻。
3. 超过 10 秒无有效速度时清空跨站上下文：这么长的缺口足以隐藏一次进站减速，不能再假定相邻停车是连续的两站。

v1 中任一坏点都会清空全部上下文，一次 GNSS 毛刺就需要再跑两个完整站间才能恢复提示。活动识别不决定手机是否固定安装，到站识别也不会开启惯性积分或改变测速与里程。

道路交通的重复平稳行驶与停车仍可能满足此模式，站间临时停车也可能与到站相似，因此始终使用推测措辞。第一版纯地下无可靠定位时不自动提示，不把速度缺失或加速度安静当成停车；继续记录原始数据供后续评估。

## JSONL 与回放

保留 schemaVersion 2，新增字段均可选，旧日志仍可读：

- `railCandidate`：按停稳时刻确定的候选 ID、算法版本、证据起点、推测停稳与检测时刻、峰值、制动时长、完整运行次数。
- `railFeedback`：用户提交的候选 ID 和 confirmed / denied 回答。
- `railResolution`：有效候选结束记录，含 stoppedAt、响应时间、confirmed / denied / unanswered 与结束原因。只有匹配仍有效候选的回答能确认到站。
- `marker.timestamp`：自动到站标记的实际候选时刻；`candidateID` 关联推测。缺省时沿用原先 receivedAt。报告与站间分析按标记时刻排序或计算。
- metadata 的 `railAlgorithmID`：此次采集使用的识别器版本。

同一个输入事件可同时保存原始观测、派生候选或结束结果。在线服务与 `SpeedReplay` 使用相同识别器和滤波器接受状态；回放忽略日志中已保存的派生候选作为识别证据，只重算原始输入和用户回答。

```sh
swift run speed-replay /absolute/path/session.jsonl > /tmp/replayed.jsonl
python3 tools/analyze_trip.py --help
```

回放输出 `rail` 包含 current、created、resolved、isRailLike；采集分析报告的 `railArrivals` 保留候选、结束结果和三类回答计数。原始高频传感器仍在同一行程中，可按候选时间定位上下文。

第一版只积累反馈，不因一次确认或否认在线改变阈值。调参应按独立行程划分验证集，对比误报、漏报、停稳到提示延迟与每次行程询问次数；未确认样本不能当负样本。旧日志如有手动标记仍可读取，但调参应与独立现场记录核对。

## 验证与剩余工作

受控测试覆盖：重复完整运行、尚在减速、降速后继续行驶、短停、突然降速、手机转动、缺失运动数据、定位失联、过期/倒序观测、步行/骑行、重复/错误候选回答、过期与恢复行驶收起、会话结束、在线与回放一致性、旧日志，以及延迟确认的标记时间。模拟器构建与记录保存流程另行核验。

v2 新增回归：巡航或制动中出现单个被拒、精度超限、跳变或缺失的定位点仍能提示；5 秒断档只放弃本段，下一站即可提示；提示期间被拒定位不收起提示。

真实列车、道路交通、车厢拿放、站间临时停车及地下区间仍需独立标签实测；受控测试与模拟器不代表真实识别率验证。

本轮验证：76 项 Swift 测试与 8 项 Python 分析测试通过，模拟器 Debug 构建通过；真实 Model/Service/Journal 的四项保存流程检查通过。独立审查发现的匀速误计制动问题已用回归测试修复；跨行程的候选 ID 也已验证可在单份记录回放时稳定关联反馈。

UI 验收边界：独立测试宿主 `Tests/RailArrivalUI` 已编译，可用 `python3 tools/test_app_flow.py --device SIMULATOR_UDID --rail-ui` 复跑布局与回调保存检查。本轮桌面工具无法访问 Simulator，现有设备有系统授权框，专用小屏设备持续停在首次启动系统迁移；因此未完成小屏布局与真实点击验收，不以构建成功替代这些检查。
