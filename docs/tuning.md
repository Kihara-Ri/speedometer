# 测速调参、回放与真机实测手册

本手册配合 [原理与参数](algorithm.md) 使用；2026-10-18 新增活动输入、出行分类输出及 speed-only reset，见 [出行识别](travel-recognition.md)。这里把**当前程序已经能做的操作**和**需要真实数据开展的调参工作**分开。本文不改变运行参数，也不代表手机上已完成道路标定。

## 1. 先确定“调得更好”怎么衡量

调参同时考虑精度、响应、可用性和误差说明，不能只让数字更稳定。

| 维度 | 应统计什么 | 需要的证据 |
|---|---|---|
| 精度 | RMSE、MAE、有符号偏差、绝对误差 P95/最大值 | 与时间对齐的独立参考速度 |
| 巡航稳定性 | 连续输出抖动、定位间外推误差 | 稳定参考速度；无真值时只能评价抖动 |
| 加速/制动响应 | 起始响应延迟、速度过冲、停止后残余速度 | 参考速度变化时刻及时间同步误差 |
| 异常鲁棒性 | 人工注入异常拒绝率、正常观测误拒率、错误重捕获 | 已知异常标签；不能把所有 outlier 都当成正确拒绝 |
| 可用性 | 可用时间占比、最长不可用区间、首次确认与恢复耗时 | 包含所有 tick 的完整记录 |
| 隧道预测 | 从最后可信定位开始，按失联年龄分桶的误差 | 隧道中仍有效的独立参考速度 |
| 误差尺度 | `abs(error) <= uncertainty`、`<= 2*uncertainty` 的经验覆盖率 | 独立真值；这些比例不是预先承诺的覆盖率 |
| 运行成本 | 采样实际间隔、回调延迟、记录体积、电量/温升 | 真机长时间采集 |

在同一评估样本集合上：

\[
e_i=\hat v_i-v_i^{ref},\quad
\mathrm{RMSE}=\sqrt{\frac1N\sum e_i^2},\quad
\mathrm{MAE}=\frac1N\sum |e_i|,\quad
\mathrm{bias}=\frac1N\sum e_i
\]

`nil` 不是真值 0，也不是误差 0。必须同时报告可用比例，避免靠大量拒绝输出获得漂亮 RMSE。比较两版算法时，分别给出各自可用率，以及共同可用时刻的配对误差；对一版额外提供预测的时间段单独列误差。

## 2. 当前合成基准，以及它实际说明什么

### 2.1 如何生成

```sh
cd /Users/kiharari/DEV/测速计
swift test
swift run speed-replay --benchmark
```

基准实现见 [Benchmark.swift](../Sources/SpeedReplay/Benchmark.swift)，保存的结果见 [benchmark.json](benchmark.json)。参数如下：

| 项目 | 当前设定 |
|---|---|
| 总时长、模拟步长 | 0…80 秒，每 0.1 秒一个评估时刻 |
| 定位 | 正常时每 1 秒一条；接收时间等于测量时间，没有人为延迟 |
| 定位速度噪声 | Box–Muller 正态噪声，标准差 0.8 m/s；原始速度截断到非负 |
| 定位报告精度 | `speedAccuracy = 0.8 m/s`，水平精度 5 m |
| 随机数 | LCG，初始种子 123456789；每个场景重新初始化 |
| 统计开始 | `t >= 5 s`，共 751 个评估时刻 |
| 固定安装 IMU | 每 0.1 秒，固定偏置 +0.15 m/s²，噪声标准差 0.05 m/s²，角速度 0 |

实际 App 请求 20 Hz IMU、约 5 Hz 输出，而基准是 10 Hz IMU、10 Hz 评估；这是当前测试设定差异，不应默认为同一采样条件。各场景真值：

| 场景 | 真值与注入条件 |
|---|---|
| `constant-noise` | 恒定 25 m/s（90 km/h） |
| `accelerate-brake` | 0…10 s 为 0；10…25 s 以 2 m/s² 加到 30；25…35 s 巡航；35…40 s 以 −6 m/s² 制动到 0；之后保持 0 |
| `train-high-speed` | 以 1.5 m/s² 从 0 加到 90 m/s（324 km/h），之后巡航 |
| `gnss-spikes` | 真值 25 m/s，在 t=0、17、34、51、68 s 的速度中额外加入 +45 m/s |
| `tunnel-handheld` | t≤20 s 正常定位，20<t<29 s 不提供定位；真值从 20 s 的 25 m/s 以 −2 m/s² 降至 17 m/s |
| `tunnel-mounted` | 同一真值/失联时段，并提供上述固定安装 IMU |

安装版与手持版的隧道场景虽然真值相同，但固定安装场景额外生成 IMU 噪声，会推进同一个随机数序列。因此两者**定位噪声样本不相同**；它们不是严格使用同一输入的配对 A/B 实验。

### 2.2 当前保存结果

所有误差单位为 m/s，乘 3.6 可转成 km/h；数值四舍五入到三位小数。

| 场景 | 原始定位时刻 RMSE | 融合定位时刻 RMSE | 连续输出 RMSE | 同时刻保持原始速度 RMSE | 连续输出最大误差 | 不可用/751 |
|---|---:|---:|---:|---:|---:|---:|
| 匀速噪声 | 0.822 | 0.616 | 0.797 | 0.827 | 2.996 | 0 |
| 加速与急刹 | 0.730 | 0.627 | 0.920 | 1.243 | 6.687 | 0 |
| 高速列车 | 0.822 | 0.652 | 0.858 | 1.026 | 2.996 | 0 |
| 定位跳点 | 10.385 | 0.637 | 0.792 | 10.447 | 2.976 | 0 |
| 隧道手持 | 0.846 | 0.636 | 1.301 | 1.170 | 7.816 | 69 |
| 隧道固定安装 | 0.774 | 0.427 | 0.489 | 1.455 | 1.112 | 39 |

统计口径要一起读：

- “原始定位时刻”只统计有定位的时刻；“融合定位时刻”还要求融合输出可用。恢复首个候选等时刻可能使样本集合不同，不能把两列之差总当成严格配对改进。
- “连续输出”每 0.1 秒统计一次，仅统计算法可用的时刻；“保持原始速度”使用**这同一组时刻**，并且保持的是上次原始速度，可能包含异常点。
- 不可用期间不计入连续 RMSE，必须看最后一列。手持/固定安装可用时刻集合不同，不能只比 1.301 与 0.489 就声称某个固定改进比例。
- `rejectedFixes` 只数返回 `outlier` 的输入，不数启动候选或其他无效输入。跳点场景显示 4 次 outlier，不等于只有 4 个注入坏点。
- `predictedSamples` 统计 `state == predicted`，不包括最近定位一秒内的模型外推；该段按输出合同仍标为 measured。

这组结果支持“合成巡航噪声有所降低、明显跳点可处理、固定安装短时制动预测有效”这几个有限结论。也揭示了待改善处：**手持隧道的连续 RMSE 比保持原始速度更差**；急刹场景最大误差约 24.1 km/h。不能用较小的全程平均误差掩盖转折点的瞬时错误。现有基准不包含真实多路径、慢姿态漂移、机车振动、系统相关误差或多设备差异。

## 4. 真机采集怎么做

### 4.1 使用当前已有入口

当前源码每次开始测速自动记录，停止测速即保存，历史详情可分享 JSONL；操作与站间距离核对见 [手持电车采集](train-recording.md)。旧安装版需更新后才有此入口。开发调试仍可在 Xcode 的 Scheme → Run → Arguments 添加 `--record-sensors`，再运行到手机；也可在终端启动安装版：

```sh
xcrun devicectl device process launch \
  --device 00008101-000319920A84001E \
  --terminate-existing dev.kiharari.Speedometer -- --record-sensors
```

其中设备标识是本次连接的 iPhone；换设备后先用 `xcrun devicectl list devices` 查实际标识。此命令启动记录，不会切换到固定安装模式。

新版记录位置为 App Documents 的 `session-<Unix秒>-<随机标识>.jsonl`，独占创建，不追加覆盖。结束写入后可以直接分享，或通过 Finder 文件共享/Xcode 下载容器取出。日志头包含模式、前向轴、设备硬件标识、应用/算法与系统版本、传感器可用性和申请采样率；源码/参数快照仍需另存。当前版本已接入后台定位，切后台或锁屏不再主动停止采样/reset；返回保留行程。系统终止/手动划掉仍会中断，应检查日志的实际采样连续性。

固定安装实验需要实际确认前向轴，并在入口中使用类似：

```swift
private let service = SpeedometerService(
    mountAxis: try! MountAxis(x: 0, y: 1, z: 0)
)
```

这里的 `try!` 只适用于写死且非零的示例向量；运行时输入应正常处理错误。手机不按该方向固定时不能照抄这个轴。每次换安装位置都重新记录说明并重启服务。预留至少 8 秒连续输入只是必要条件，还需模型偏置门限满足；不能只凭等待时间认定校准完成。

### 4.2 每段行程至少记下这些信息

| 信息 | 原因 |
|---|---|
| 日志文件名、采集日期、代码版本/源码快照、参数改动 | 新版已有应用/算法标识，仍需保存实际源码与改动参数；旧日志没有元数据头 |
| iPhone 型号、iOS 版本、定位精度授权 | 设备与系统差异可能影响观测 |
| 电车/汽车/摩托车、实际安装位置、手持/固定安装、前向轴 | 不能把一种安装条件的参数结论直接移给另一种 |
| 起步、巡航、制动、停站、进出隧道、拿动手机的事件时间 | 定位误差与响应要按阶段看 |
| 参考速度来源、采样率、时钟对齐方法、估计同步误差 | 缺少时间同步时，参考值也会制造假误差 |
| 是否有参考速度、哪些区间缺失 | 无真值的区间不能输出“绝对精度”结论 |

新版 JSONL 记录经纬度、定位 callback error、内部 a/b/P、最近定位创新/NIS、输入结果与不确定度构成，电脑工具可导出诊断 CSV。参考速度仍需独立采集与对齐；详细惯性门控原因没有逐项分解。旧版日志没有这些新增字段。

### 4.3 怎样选择参考速度

优先采用独立且有明确时间戳/精度说明的参考源。车辆仪表可以提供实用对照，但应记录其分辨率、滞后和可能的系统偏差；不直接当作无误差真值。同一部 iPhone 的另一个 GPS App 往往共享观测条件，只能做交叉对照，不能自动算独立真值。

参考时间对齐必须独立处理。比如减速度为 6 m/s² 时，0.2 秒同步误差本身就能引入约 1.2 m/s（4.32 km/h）的表观速度差。不能靠随意平移结果曲线，让某组参数看起来更准；对齐规则须在比较参数前固定。

没有参考速度的电车记录仍可检验时序、异常拒绝、预测超时和停站恢复，但不能验证隧道内绝对速度。数据采集由乘客或固定设备完成，避免让驾驶者操作手机。

## 5. 离线回放与故障注入

### 5.1 原样回放

```sh
cd /Users/kiharari/DEV/测速计
mkdir -p .build/tuning/baseline
# 将实际采集文件复制到下述路径后执行：
swift run speed-replay .build/tuning/session.jsonl \
  > .build/tuning/baseline/estimates.jsonl
# 仅对包含已投影 motion 的固定安装记录：
swift run speed-replay .build/tuning/mounted-session.jsonl --mounted \
  > .build/tuning/baseline/mounted-estimates.jsonl
```

每个非空输入行对应一个输出行，包含 `result` 和 `estimate`。接收时间允许相等，不能倒退；测量时间可以倒序，以检验拒绝路径。两种观测不能塞在同一事件，reset 也不能与观测同放。非法 JSON 或事件歧义会使 CLI 返回失败，不会悄悄略过；空行会被忽略。

原始 `rawMotion` 只是记录数据；回放器不会从它重新计算投影、检查安装姿态或构造 `motion`。因此：

- 对手持日志加 `--mounted` 不会自动获得惯性辅助。
- 调整前向轴、g 换算、四元数或安装门限，不能仅靠现有回放器验证该修改；它会继续使用已记录的投影观测/拒绝标记。
- 调整核心滤波参数，可以对同一已投影输入直接重放。
- 新版保存了定位墙钟时间、接收墙钟时间及单调时间，可以用于离线检查时钟桥接；现有回放器仍直接使用已转换的 `speed.timestamp` 和记录的 reset，并不重新执行完整 iOS 适配层。旧版日志没有上述墙钟与位置字段。

### 5.2 故障注入应改什么

保留原始日志，另生成注入版本；每种注入保存起止时间及事件标签。

| 目的 | 修改方式 | 预期检查 |
|---|---|---|
| 模拟卫星速度中断 | 只去掉指定区间的 `speed` 观测事件，保留 motion、tick、reset | 先预测，普通最长 3 秒、可信惯性最长 6 秒，之后无速度 |
| 定位瞬时大跳 | 对单条 speed 加/减速度偏移，不改 reported accuracy | 检查是否被识别；小而物理可行的跳点并不保证拒绝 |
| 无效速度精度 | 将 speedAccuracy 设为 −1 | 返回 invalid，不刷新 lastFix |
| 重复/乱序测量 | 保持 receivedAt 顺序，只复制或倒退 `speed.timestamp` | 返回 outOfOrder，不延长有效时间 |
| 定位回调延迟 | 增加被延迟事件的 receivedAt，并与其他事件按新接收时间稳定归并 | ≤2 秒按近似补偿，>2 秒 stale；不能把整个日志时间都平移来冒充延迟 |
| 运动中断 | 去掉一段 motion 事件但保留 tick/定位 | 可信惯性因新鲜度失效；恢复需重新累计连续采样跨度 |
| 安装转动的核心分支 | 将一条投影 motion.rotationRate 设为 >0.25 | 锁定禁用惯性，定位仍可用；不能代替真实四元数投影链验证 |
| 偏置变化 | 给 motion.acceleration 加已知偏置/漂移，保留真值副本 | 评估收敛、失联后误差和错误可用率 |

如果记录中只有定位而没有 tick，把所有失联区间的行删掉后，回放器没有机会在中间输出超时结果；必须显式补充时间推进事件。当前 iOS 正常前台日志已有约 5 Hz tick，但主线程卡顿时仍可能有空档。

### 5.3 一个可以直接跑的输出统计例子

以下只统计结果，不计算没有参考速度的“精度”：

```sh
python3 - <<'PY'
import json
from collections import Counter
from pathlib import Path
p = Path('.build/tuning/baseline/estimates.jsonl')
rows = [json.loads(line) for line in p.read_text().splitlines() if line.strip()]
print('events:', len(rows))
print('ingest:', dict(Counter(row.get('result', 'tick') for row in rows)))
print('states:', dict(Counter(row['estimate']['state'] for row in rows)))
PY
```

这是事件计数。日志混有 20 Hz 运动、5 Hz tick 和不定频定位，事件占比不等于时间可用率。严谨时间指标要统一到固定网格，或按相邻事件的时间跨度积分；也不要把大量重复输出当作独立样本估计置信区间。

## 6. 调参顺序与建议的实验范围

下面范围仅是**准备开展实验的搜索范围**，没有写入程序，也没有证明在真实设备上更优。先用多个正常行程建立基线，再每次改一组有明确问题证据的参数。把不同完整行程分成调参集和保留验证集；同一行程随机切帧会让相邻相关样本泄漏到两边。

### 第一步：先排除时间和安装错误

检查测量与接收时间、实际 IMU 间隔、授权、坐标轴方向、记录是否前后台中断。时间不同步或前向轴反了，调 Q/R 很难补救。确定这些无误后，再看定位速度本身是否存在偏差；滤波器不能凭空消除持续一致的系统偏差。

### 第二步：校准定位权重 R

在有参考速度且时间对齐的定位时刻，按 `speedAccuracy` 分桶统计真实残差，检查它是否随报告精度增大；静止和巡航分开统计。近零速度有非负截断，残差分布不应直接当作未截断高斯。

先试速度精度下限 `0.25 / 0.35 / 0.5 / 0.8 m/s`，不要把负 accuracy 改成可用。当前没有 `R` 的额外缩放参数；如需拟合 `R = c²σ² + floor²` 一类模型，是有公式和测试变更的代码改动，需与当前 `max(0.35, accuracy)²` 方案分别评估。

R 增大通常更平滑、更依赖模型，也可能更慢；R 太小容易相信异常。若主要问题是定位间的虚假加速度，优先检查 Q，而不是只把 R 放大。

### 第三步：调巡航过程噪声与机动响应

| 参数 | 当前 | 建议单独试验值 | 增大时主要影响 |
|---|---:|---|---|
| 普通 jerk PSD q | 0.2 m²/s⁵ | 0.05、0.1、0.2、0.5、1 | 加速度更容易变化，可能更快，也可能把定位噪声外推 |
| 机动 jerk PSD | 4 m²/s⁵ | 1、2、4、8 | 明显加减速时更快校正，可能增加过冲 |
| 机动触发创新 | 2.5 m/s | 1.5、2.5、4 | 数值增大意味着更少触发，巡航更安静但机动可能更迟 |

分别统计定位时刻和两次定位之间的误差。出现“定位到来时准，下一秒前越来越偏”通常提示加速度估计/外推问题。出现“急刹第一秒落后，后面正常”要区分定位采样固有限制、接收延迟和滤波滞后。

不要只凭一个匀速场景选最小 q。必须同时检查起步、停止、制动结束后、低速和高速度转折。当前急刹基准的最大误差较大，属于需要重点按时刻检查的案例。

### 第四步：调异常门限与确认链

NIS 上限可先离线比较 `9 / 16 / 25 / 36`，但必须同时标注正常强制动的误拒情况。更小通常更严格，也更可能拒绝真实机动。物理加速度上限 12 m/s² 同时用于多个代码位置，不能只改其中一处后解释成统一新模型。

重新捕获次数增加，会减小单点接管风险并延长恢复。当前启动 2 次、连续异常 3 次：没有真实恢复样本之前，不建议为减少等待把启动改成单点输出。即使三个候选相容，也只能说明与候选链相容，不是外部验证。

### 第五步：标定固定安装 IMU

先核实安装轴，再使用有 GNSS 的固定安装记录，观察不同制动/加速阶段投影加速度与参考速度变化是否方向一致。不要把安静 IMU 当作静止证据，也不要在长失联时用自己的预测反过来当真值校偏置。

可试验：`R_a = 0.09 / 0.36 / 1.0 (m/s²)²`；偏置随机游走 PSD `0.0001 / 0.0004 / 0.0025 m²/s⁵`。更大 R_a 更少相信单帧 IMU；更大 q_b 允许偏置变化更快，但也可能把真实加速度吸进偏置。

连续时间门限可研究 8/12/20 秒，偏置标准差门限可研究 0.2/0.3 m/s²，前提是记录支持收敛评估。不要因为门限难通过就直接放宽：车体转弯触发姿态禁用，可能反映当前固定轴模型不适合该段运动，应单独统计退回定位的比例。

### 第六步：最后决定隧道可预测多久

手持的 3 秒、固定安装的 6 秒是上限，不是误差承诺。按失联年龄分桶，例如 0…1、1…2、2…3、3…4、4…6 秒，分别报告参考误差 P95、最大误差、模型误差尺度、可用率和失败案例。

先选择应用能接受的误差目标，再用保留行程验证达到目标的时长。没有隧道内真值时，只能确认超时逻辑，不能把时限调长后宣称覆盖了更长隧道。当前 8 m/s 的误差尺度截止约为 28.8 km/h，数值并不小；若日常可读性要求更严格，应基于实测收紧，不应因算法仍有输出就认定可靠。

对增长下限的调整要和 `P_vv` 一起看：实际输出取二者最大值。单独减小 0.75、0.35、0.12 可能只让误差说明显得乐观，不会使速度本身更准确。

## 7. 一次参数试验如何留下可复核结果

1. 保存原始采集文件及采集说明，不覆盖原件；标明手持或固定安装。
2. 保存当前源码版本/快照、基线参数、完整测试与基准输出。
3. 只改变所研究的参数组，重新构建回放器，对同一输入回放到独立目录。
4. 运行 `swift test`。关键回归失败时，先判断是行为退化还是经过讨论的新约束，不能直接放宽测试来掩盖问题。
5. 对齐独立参考，比较共同可用时刻误差、各自可用率、制动延迟、异常误拒、恢复耗时及最差片段。
6. 在保留行程上复核，记录“保留/回退”的原因，再决定是否更新 App。

基线命令示例：

```sh
cd /Users/kiharari/DEV/测速计
mkdir -p .build/tuning/baseline
swift test > .build/tuning/baseline/tests.log 2>&1
swift run speed-replay --benchmark > .build/tuning/baseline/benchmark.json
```

每次试验建议保存一张记录表：

| 字段 | 需要填写的内容 |
|---|---|
| 实验与数据 | 实验编号、日期、行程文件、参考来源、调参集/保留集 |
| 参数 | 源码版本、修改位置、修改前后数值及单位 |
| 假设 | 观察到的问题，以及预计这组参数为何能改善 |
| 总体结果 | RMSE/MAE/P95、有符号偏差、可用率 |
| 分阶段结果 | 巡航、加速、急刹、停止、失联年龄桶、恢复 |
| 反例 | 最差误差片段、误拒真实制动、错误重捕获、惯性禁用原因 |
| 决策 | 保留或回退；尚未覆盖的实际条件 |

目前已有记录界面、诊断 CSV 和按站间距离比较速度积分的工具；见 [手持电车采集](train-recording.md)。尚没有自动搜索器、独立瞬时参考速度导入/对齐工具或完整诊断面板。站间距离比较不能替代逐时刻速度精度验证。
